# DPIA Template: Customer-Facing AI Chatbot

A data protection impact assessment structure for customer-facing chatbots that use large language model APIs, such as those from OpenAI, Anthropic or Google, to handle support, sales or information queries.

## How to use

Complete each section for the chatbot you are actually deploying, replacing the bracketed placeholders. Where a section does not apply, say so and record why.

- General customer support: legitimate interests (Article 6(1)(f)), supported by a legitimate interests assessment

- Marketing use of conversations: consent (Article 6(1)(a)), where consent is the appropriate basis

## 3. Personal data inventory

**Data provided by users:**
- conversation text, which may contain anything a user chooses to type;
- user identifier, such as a session ID or account ID where the user is logged in;
- IP address and device information;
- phone number, where the channel is WhatsApp or SMS.

**Data sent to the model provider:**
- the user's query after filtering on your own server;
- the system prompt and relevant context;
- recent conversation history (record how many turns).

**Data not sent to the model provider:**
- full customer records, or database fields not needed for the response;
- payment information;
- identity documents.

**Data generated by the chatbot:**
- AI-generated responses;
- metadata, such as confidence scores;
- flags, such as a decision to escalate to a person.

**Retention:**
- full conversation transcripts: [X days]
- conversations marked as resolved: [Y days]
- audit logs: [Z days, with the reason for the longer period]

```
User → web or messaging interface → your server (chatbot orchestration)

  → model provider API [provider, region]
  → response returned to your server
  → optional lookup in your knowledge base
  → final response to the user
  → conversation logged to your database [region]
```

## 5. Risk assessment

**5.1 Inappropriate disclosure by the chatbot**
- Likelihood: medium, because models can produce inaccurate output or repeat information they should not
- Severity: depends on the data in scope
- Mitigation: restrictions in the system prompt, content filtering and escalation triggers

**5.2 More personal data reaching the model provider than is needed**
- Likelihood: high without controls
- Mitigation: filtering on your own server before each API call, and minimisation in how prompts are constructed

**5.3 Conversation logs as a target for attack**
- Likelihood: low where encryption and access controls are applied
- Mitigation: encryption at rest, role-based access and retention limits

**5.4 A breach at the model provider, or dependence on a single provider**
- Likelihood: low, with significant consequences
- Mitigation: provider due diligence, a breach notification clause in the data processing agreement, and conversation data held in a portable form

**5.5 Users not realising they are talking to an AI system**
- Article 50(1) of the EU AI Act, which has applied since 2 August 2026, requires AI systems that interact directly with people to be designed so that people are told they are interacting with AI, unless that is obvious from the context. The privacy notice must also describe the processing under Articles 13 and 14 of the GDPR.
- Mitigation: a clear disclosure at the start of each conversation

**5.6 Handling data subject rights**
- A subject access request needs to return every conversation linked to the user, and an erasure request needs to remove conversation history throughout, including any copies held by the model provider.
- Mitigation: an access and erasure process tied to the user identifier, including a step to confirm deletion with the provider where it holds data

## 7. Residual risk and sign-off

**Residual risk:** [low, medium or high]

**Approval:**

**Review:**
